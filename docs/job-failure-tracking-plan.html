HR BG Service — Job Failure Tracking Plan

Scope: hr-bg-service (Lumen 10 + RabbitMQ) and task-scheduler (FastAPI + APScheduler) • Written 2026-10-28 • Estimate: ≈ 8 working days across 6 phases

Goal

Every background job run gets one row in job_runs that says what happened, why, how long it took, what it wrote or rolled back, and what it logged. A watchdog catches the things that leave no row (missed schedules, dead workers, stuck queues). Problems go to one alert channel with dedupe and a "resolved" message. Nothing in the existing job classes has to change for the core to work.

Status model

One final status per run, plus flags that can stack on any status.

StatusMeaningWritten byAlert
queued / runningIn flightTrigger consumer / Queue::before—
successFinished, no error logged, nothing rolled backQueue::afterSends "resolved" if an alert was open
completed_with_errorsReturned normally, but logged at error levelQueue::after + log tapAmber, deduped
partialSome transactions committed, some rolled backQueue::after + DB tx eventsAmber, deduped
rolled_backEvery write undone, but the job returned normallyQueue::after + DB tx eventsRed
failedThrew after the last attempt, nothing committed. Safe to retry.Queue::failingRed
failed_retry_unsafeThrew after committing writes. A retry would apply them twice.Queue::failingRed, auto-retry blocked
timed_outKilled at timeout, or still "running" past max_runtimeWorker (pcntl) / watchdogRed
lostWorker died mid-run (OOM, container kill). Fatal reason stored if available.Shutdown handler / watchdogRed
trigger_failedTrigger message unparseable or not dispatchable. Raw body kept for replay.Trigger consumerRed
missedSchedule was due and no run started within the grace periodWatchdogRed
stuckQueue has messages but 0 consumers, or its oldest message is too oldWatchdogAmber

Flags: late (time from queued to started over max_wait), zero_output (reported count is 0 or below 20% of the 7-day median), slow (duration over 80% of max_runtime or 2× the 7-day p95). Flags are shown on the dashboard. late and zero_output also alert (amber).

Data model

All tracking tables are written through a separate DB connection named tracking (same credentials as mysql, its own PDO). A job's DB::rollBack() can therefore never erase its own tracking row. All timestamps are written from PHP in Asia/Dhaka, never by MySQL defaults.

job_runs

  • id, run_uuid (unique, also put in every log line's context)
  • job (queue base name, e.g. processTempData), job_class, queue
  • trigger_source (scheduler / api / retry / catchup / manual), triggered_by (user id), parent_run_id (for retries)
  • payload json, status, flags json, attempt, max_attempts
  • queued_at, started_at, finished_at, wait_ms, duration_ms
  • worker_host, worker_pid
  • error_class, error_message, error_trace
  • tx_committed, tx_rolled_back, writes_kept, writes_undone, http_calls, http_failed
  • errors, warnings, log_lines, log_dropped, log (gzipped json, MEDIUMBLOB)
  • metrics json (e.g. {"attendance": 512})
  • Indexes: (job, started_at), (status, started_at), (queued_at)

job_schedules

  • job (PK), queue, cron, timezone
  • grace_minutes, max_runtime_s, max_wait_s
  • expect_metric (metric key to watch for zero output, nullable)
  • enabled, source (scheduler registry / manual), synced_at
  • last_expected_at, last_checked_at

Also holds the on-demand jobs (no cron) so they get max_runtime and max_wait.

job_alerts

  • job, kind (status or flag), first_run_id, last_run_id
  • opened_at, last_sent_at, occurrences, resolved_at

heartbeats

  • name (PK: watchdog, worker, trigger_consumer, scheduler), beat_at, info json

failed_jobs

  • Laravel standard table (php artisan queue:failed-table), driver database-uuids

  2.   4. start-worker.sh: HR_BG_WORKER_TRIES 100 → 3, add --backoff=30,120,600. Raise --timeout to the longest job's limit and set per-job public $timeout on the heavy ones (ProcessTempSalaryJob, ProcessRealSalaryJob, CacheRegenerateJob).
  5. .env: QUEUE_FAILED_DRIVER=database-uuids. Create the failed_jobs migration and run it.
  6. Remove the token from the log line at CreateDeviceUserByEmpCode.php:32.
  7. Decide on legacySync_trigger_queue: add a consumer, or stop publishing it from the scheduler.

Done when: scheduler is up; a job that throws lands in php artisan queue:failed after 3 attempts; php -m lists pcntl.

Phase 1 — Run ledger 2 days

  1. config/database.php: add a tracking connection (copy of mysql).
  2. Migrations: job_runs, job_schedules, job_alerts, heartbeats.
  3. app/Support/RunTracker.php: holds the current run's state.
    • Counts transactions and writes using a stack (handles nested savepoints and rollBack($toLevel)).
    • Buffers log lines: collapses consecutive repeats; keeps the first and last 2,500 lines; redacts password, token, secret and authorization keys and JWT-looking strings; truncates context to 4 KB.
    • Flushes to the DB on every error line and every 30 s, so a hard kill loses at most 30 s of info lines.
    • Decides the final status (see status model).
    • On a clean success, keeps only warnings, errors and the first and last 25 other lines.
    • Rolls back any transaction a job left open, so it can't leak into the next job.
    • RunTracker::metric($key, $n) for output counts.
  4. app/Providers/JobTrackingServiceProvider.php, registered in bootstrap/app.php:
    • Queue::before → row running, RunTracker::start(), Log::shareContext(['run_id' => …])
    • Queue::after → RunTracker::finish(false)
    • Queue::exceptionOccurred → record the attempt's error; if writes_kept > 0, call $job->fail() to stop auto-retry
    • Queue::failing → RunTracker::finish(true)
    • DB events: QueryExecuted, TransactionBeginning, TransactionCommitted, TransactionRolledBack (ignore the tracking connection)
    • MessageLogged → log tap
    • HTTP client events ResponseReceived / ConnectionFailed → http_calls, http_failed (ZKBio calls can't be rolled back, so they're at least counted)
    • register_shutdown_function → if a run is open and error_get_last() is fatal, mark the run lost with the message
    • Queue::looping → heartbeats.worker
  5. RabbitMQJob calls other jobs' handle() inline. Record the target queue as job, not RabbitMQJob, so runs are grouped correctly.
  6. ConsumeTriggerQueues:
    • Insert the queued row and carry its run_uuid into the dispatched job.
    • On bad JSON or a dispatch error, insert trigger_failed with the raw body (instead of silently dropping it), then ack.
    • Read triggered_by and trigger_source from the payload when present.
    • Write heartbeats.trigger_consumer.
  7. tests/RunTrackerTest.php: status decision (all branches), nested savepoint rollback, rollBack($toLevel), log trimming on success, redaction.

Done when: every scenario in the verification matrix rows 1–7 produces the expected row; tests pass.

Phase 2 — Watchdog 1.5 days

  1. app/Console/Commands/JobsWatchdog.php (jobs:watchdog), run every 60 s from a third loop in start-worker.sh. Each check runs on its own, so one failing check doesn't stop the others.
  2. Missed: for each enabled schedule, compute the last expected fire time with dragonmantank/cron-expression (already in vendor) in Asia/Dhaka. If no run of that job has started since expected + grace, insert a missed row with the payload it would have sent (for "run now").
  3. Timed out / lost: running rows older than max_runtime. Mark lost if the worker heartbeat is stale, otherwise timed_out.
  4. Late: queued rows older than max_wait get the late flag.
  5. Stuck: RabbitMQ management API (:15672/api/queues): messages > 0 with consumers = 0 for 10 min, or the oldest message older than N min. Covers legacySync-style orphans.
  6. Zero output / slow: compare the latest run's metrics and duration_ms with the 7-day median and p95.
  7. Schedule sync: task-scheduler publishes its job list (id, queue, cron, next_run_time) on startup to schedulerRegistry_trigger_queue. The existing naming convention resolves this to a new SchedulerRegistryJob, which updates job_schedules. There's then one source of truth for cron times: the CRON_* env vars.
  8. Cross-watch: the scheduler calls GET /api/jobs/health every 5 min. If the watchdog heartbeat is older than 3 min, or hr-bg doesn't answer, the scheduler posts the alert itself. The watchdog checks heartbeats.scheduler (written by the registry and health pings) the same way.
  9. Retention: null out log on success rows after 7 days, delete rows after 90 days, delete resolved alerts after 90 days.

Done when: verification matrix rows 8–13 behave as expected.

Phase 3 — Alerts 1 day

  1. app/Support/Alert.php: one channel (default Slack incoming webhook, JOB_ALERT_WEBHOOK_URL), using the HTTP client already used by the jobs.
  2. Dedupe by (job, kind) in job_alerts:
    • Send once when an alert opens, then at most one reminder per hour, with a count ("failing 37×").
    • Send one "resolved" message on the next success.
  3. Each message includes the job, status, reason (first error line), run link, attempt, duration, writes kept/undone, and "retry unsafe" when relevant.
  4. Daily digest at 09:00: runs per status per job, open alerts, slowest jobs.
  5. The scheduler's cross-watch alert uses the same webhook from Python.

Done when: a job that fails every minute sends 1 alert plus hourly reminders, and a single "resolved" message once it passes.

Phase 4 — API and dashboard 1.5 days

  1. Auth first: put /api/jobs/* behind the same auth the api-gateway uses (or an internal token header as a fallback). Retry, replay and run-now endpoints additionally require an admin role.
  2. Endpoints:
    • GET /api/jobs/runs: filter by job, status, flag, date range; paginated
    • GET /api/jobs/runs/{id}: full row plus decompressed log, filterable by level
    • GET /api/jobs/summary: per job, last run, last success, 24h counts, open alerts
    • GET /api/jobs/health: heartbeat ages (used by the cross-watch)
    • POST /api/jobs/runs/{id}/retry: re-dispatches the payload with parent_run_id; refuses failed_retry_unsafe unless force=1, and the force is logged with the user
    • POST /api/jobs/runs/{id}/replay: for trigger_failed
    • POST /api/jobs/missed/{id}/run-now: catch-up with trigger_source=catchup
  3. Page: per-job health grid, problem-runs table, run detail with a log viewer that shows tx lines between log lines. Served by Lumen now; it can move to the React front end later because it only calls the API.

Done when: without auth every endpoint returns 401; with auth you can find any run from the last 90 days and retry it.

  4. Review the completed_with_errors rows from the first week. Change catch blocks that hide real failures to rethrow, starting with the salary and attendance jobs.

Known limits

  • Soft failures are caught only when the job logs at error level. A job that bails out with Log::warning or returns silently still counts as success; the zero_output check is the safety net there.
  • Write counts are SQL statements, not rows (a 500-row bulk insert counts as 1). QueryExecuted doesn't expose affected rows.
  • HTTP side effects (ZKBio, SMS) are counted, but can't be rolled back.
  • If MySQL is down, nothing can be written to the tracking tables; the daily log file (with run_id) is the fallback. If both containers are down, only an external uptime monitor would notice.
  • One worker process means one job at a time. Tracking makes the delay visible but doesn't remove it. Splitting heavy queues onto a second worker is a separate decision.
