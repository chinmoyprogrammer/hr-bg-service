MBW HRM — Backend API Development Schedule (CRUD-first)

Timeframe: 5 months ≈ 20 weeks • Capacity: 24 days/month × 8h/day × 5 months = 960h

Scope & Assumptions (Backend-only)

  • Focus on simple CRUD APIs for entities listed in BRS and Sheets: SortedTables1 (tables) and APIList1 (endpoints).
  • Services already running: api-gateway, auth, crm, hrm, notification, rabbitmq, redis, reporting.
  • Primary implementation targets: hr-admin-backend, crm-backend, reporting-backend (and reporting-backend-go/nodejs where applicable). All APIs exposed behind api-gateway-docker-micro-service.
  • Each API set delivers: Create, Read (list/detail), Update, Delete, server-side pagination/filter/sort, audit fields, standard error format.
  • Demo-first approach: weekly target includes seed data, Postman/cURL scripts, and gateway route checks.

Methodology

  • Weekly cadence (20 weeks) targeting API groups aligned to “pages” in the BRS.
  • Standard contracts from APIList1; entities from SortedTables1.
  • Consistent API shape: GET /v1/{entity}, GET /v1/{entity}/{id}, POST /v1/{entity}, PUT /v1/{entity}/{id}, DELETE /v1/{entity}/{id}.
  • Definition of done per week: endpoints, validation, RBAC middleware, audit logging, pagination, error normalization, gateway mapping, demo scripts.

Demonstration Method (Backend)

For each API group (corresponding to a page), demonstrate:

  • Create: POST returns 201 with resource; validates required fields; audit fields set.
  • List: GET supports ?page,size,sort,filter,q; returns 200 with pagination meta.
  • Detail/Update: GET/{id} and PUT/{id} return 200; preserves audit trail.
  • Delete: DELETE/{id} returns 204 (or 200 with body) and enforces soft-delete if policy.
  • RBAC: verify access by role via auth middleware and claims; deny returns 403.
  • Error format: { errorCode, message, details } with consistent HTTP status codes.
  • Gateway: route registered under /api/v1; CORS and rate-limiting configured.

API Deliverable Definition (CRUD-first)

API Aspect Definition of Done
Create POST returns 201; validates required fields; sets audit fields; emits events where needed.
List Server-side pagination; sorting; keyword search; column filters; response includes meta (total,page,size).
Update PUT returns 200; idempotent; audit fields updated; business validation applied.
Delete DELETE returns 204 (or 200); soft-delete flags if policy; cascade rules respected.
RBAC Auth middleware validates roles/permissions; secure defaults; 401/403 on unauthorized.
Docs & Demo Postman collection or cURL scripts; demo steps; seed/test data; gateway route verified.

Example Demo Script (Companies API)

  1. Authenticate and obtain token via auth service.
  2. Create: curl -X POST "$GATEWAY/api/v1/companies" -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"name":"MBW Ltd","industry":"Manufacturing"}' — expect 201 with JSON body.
  3. List: curl "$GATEWAY/api/v1/companies?page=1&size=10&q=MBW" -H "Authorization: Bearer $TOKEN" — expect 200 with pagination meta.
  4. Update: curl -X PUT "$GATEWAY/api/v1/companies/{id}" -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" -d '{"industry":"Textiles"}' — expect 200 and audit changed.
  5. Delete: curl -X DELETE "$GATEWAY/api/v1/companies/{id}" -H "Authorization: Bearer $TOKEN" — expect 204 or soft-delete confirmation.
  6. RBAC: repeat calls with a role lacking write permission — expect 403.
